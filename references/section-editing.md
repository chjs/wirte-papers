# 문장·문단·절별 편집 절차

이 절차는 Strunk의 명료성 원칙과 공개된 학회·저자 조언을 시스템 논문에 적용한 **도출 절차**다. 저자의 의도·근거·논문 유형에 맞춰 사용하고, 모든 논문에 동일한 목차를 강제하지 마라. 학회별 출처는 [conference-guidance.md](conference-guidance.md), Simon Peyton Jones의 집필·독자 중심 조언과 적용 예외는 [principles-and-sources.md](principles-and-sources.md)에 있다.

## 연구 초기: 쓰면서 질문을 구체화하기

아이디어·초기 초안의 집필을 요청받았을 때 사용하라. 완성된 문장 한 개를 교정하는 요청에 이 과정을 덧붙이지 마라.

1. 제공된 문제·관찰에서 **잠정 핵심 메시지와 기여**를 작성하라. 사실, 가설, 설계 목표, 미구현 기능을 표시하고 아직 모르는 연결을 단정하지 마라.
2. 짧은 개요나 요청된 문단을 쓰면서 설명이 막히는 지점을 찾으라. 막연한 ‘자료 부족’ 대신 해당 문장과 연결된 질문을 적어라. 예: 특정 메커니즘의 효과를 주장하는데 비교에서 다른 설정도 함께 달라졌는가?
3. 질문마다 현재 자료로 답할 수 있는 것과 추가 분석·실험이 필요한 것을 나누라. 필요한 최소 근거와 그 결과가 어떤 주장을 바꿀지 제안하라. 요청 없이 실험을 실행하거나 결과를 생성하지 마라.
4. 새 근거가 제공되면 메시지·범위·기여표를 다시 조정하라. 처음 쓴 이야기를 유지하기 위해 불리한 결과를 제외하지 마라.

초기 초안의 빈칸은 질문·계획으로 남겨도 된다. 성과가 정해진 것처럼 Abstract의 개선율이나 Conclusion을 미리 완성하지 마라. 미확인 사실은 작업용 표식으로 표시하고, 사용자에게 확인된 문장과 구별해 전달하라.

## 절을 쓰기 전에: 무엇이 새로 알려지는가

Introduction 작성이나 전체 논증 리뷰에는 다음 기여표를 필요한 만큼 사용하라. 사용자가 기여를 이미 정리했다면 새 양식을 강요하지 말고 그 자료를 보완하라.

먼저 독자가 재사용할 수 있는 **핵심 통찰을 한 문장**으로 적어 보라. 환경·조건을 생략해야만 강한 메시지가 된다면 범위를 줄여라. 초기 연구라면 잠정 가설임을 표시하라. 여러 설계 요소·측정 결과·운영 교훈이 한 메시지를 뒷받침할 수 있다. 정확히 한 기여만 남기거나 하나의 일관된 시스템 논문을 기계적으로 쪼개지 마라. 공통 메시지가 아직 불분명하면 억지로 만들지 말고 후보와 차이를 제시하라.

| 문제·대상 환경 | 가장 관련 있는 선행 접근과 실제 한계 | 새 지식·아이디어·교훈 | 구현·분석 상태 | 근거 위치와 한계 |
|---|---|---|---|---|
| 누가 어떤 비용·제약을 겪는가 | 확인한 문헌·설정과 차이 | 선행 지식에 무엇이 추가되는가 | 제안/구현/배포/측정/증명 | 본문·결과 자료 또는 미확인 |

설계 논문은 선택의 이유와 효과, 측정 논문은 새 관찰과 기존 설명의 수정, 운영 경험은 맥락·실패·교훈과 전이 가능성을 중심으로 읽어라. ‘구현했다’는 사실만으로 학문적 기여를 설명했다고 판단하지 마라. 반대로 운영 트랙에 새 알고리즘이 없다는 이유만으로 기여를 부정하지 마라. 연구 유형과 실제 트랙 기대를 함께 확인하라.

선행 연구를 읽지 않았으면 비교의 정확성을 확인했다고 하지 마라. 모호한 ‘기존 시스템은 모두’ 대신 비교 대상과 조건을 특정하고, 문헌 검색이 별도로 필요하면 그 주장을 미확인으로 남겨라.

## 문장: 무엇이 무엇을 하는가

1. 주어·동사·대상을 찾고 한 문장에서 전달할 핵심 관계를 정하라. 명사화는 동사로 바꾸되 분야의 정확한 명칭까지 풀어쓰지 마라.
2. `this`, `it`, `which`, `respectively`, `only`의 대상과 범위를 확인하라. 선행사가 둘이면 명사를 반복하라. 행위자가 알려지지 않은 수동태를 `we`로 바꾸지 마라.
3. 동일한 개념은 동일한 이름으로 유지하라. `request`, `query`, `job`을 문체 때문에 번갈아 쓰지 마라. 명확한 전문 용어의 반복은 허용하라.
4. 조건·비교 대상·인용을 해당 주장 가까이에 두라. `under saturation` 같은 조건을 다른 결과에도 적용되도록 옮기지 마라.
5. 비교할 항목은 같은 측정량과 문법 구조로 쓰라. `compared with B`가 시스템인지 지연 수치인지 명확히 하라.
6. 인과·시간·대조·예시 중 실제 관계를 드러내라. 관계가 확인되지 않으면 단순 나열을 허용하라.
7. 문장 길이가 아니라 해석 부담을 기준으로 나누거나 합치라. 필요조건, 예외, 적용 범위가 결과에서 떨어져 나가지 않게 하라.

정보 흐름을 고칠 때는 앞 문장에서 이어받는 대상이 문두에서 보이고, 새 핵심이 눈에 띄며, 주어와 동사 사이에 과도한 삽입이 없는지 보라. [Gopen–Swan의 독자 기대 관점](https://www.usenix.org/sites/default/files/gopen_and_swan_science_of_scientific_writing.pdf)을 적용하되, 중요 정보를 무조건 문장 끝으로 옮기는 공식으로 쓰지 마라. 기존 주제를 이어 주는 수동태는 적절할 수 있다.

## 문단: 한 가지 독자 질문에 답하기

문단의 역할을 짧게 붙여 보라: ‘왜 문제가 생기는가’, ‘왜 이 선택인가’, ‘이 실험이 무엇을 보여 주는가’. 둘 이상의 독립적인 질문이면 분리를 고려하라.

- 첫 부분: 독자가 이미 아는 대상과 새 논점의 관계를 제시하라. 필요한 연결 문장이 먼저 와도 된다.
- 중간: 정의·메커니즘·측정·예시 중 해당 논점을 지지하는 내용을 배치하라. 설계 의도와 관찰 결과를 구분하라.
- 끝: 지지된 함의나 다음 논점과의 연결을 제시하라. 모든 문단에 “Thus, …”를 덧붙이지 마라.
- 인접 문단: 같은 용어가 같은 대상을 가리키는지 확인하라. 핵심 정의를 독자가 처음 필요로 하는 지점에 두라.
- 압축: 문장을 없애도 해당 주장에 필요한 근거와 조건을 독자가 복원할 수 있는지 확인하라.

## Abstract

문제·핵심 아이디어·구현/분석 상태·대표 결과·범위를 담되, 본문 목차를 나열하지 마라. 모든 분야에 고정 문장 수를 강제하지 마라. 결과는 Evaluation의 동일한 지표·baseline·집계 방식과 연결하라. 전체 범위를 대표하지 않는 최고 기록을 무제한 성능 주장으로 바꾸지 마라. 결과가 아직 없으면 목표와 계획으로 구분하고 측정된 것처럼 쓰지 마라.

## Introduction

다음 질문에 답하도록 순서를 설계하라. 한 질문이 여러 문단이 될 수도 있다.

| 독자 질문 | 작성·편집 행동 | 피할 오류 |
|---|---|---|
| 누구의 어떤 문제가 왜 중요한가? | 구체적 동작 환경과 관찰 가능한 비용을 제시하라. | 근거 없는 시장 규모, ‘폭발적 증가’, 모호한 중요성 |
| 기존 방법은 어떤 조건에서 부족한가? | 관련 연구의 실제 가정·메커니즘·한계를 인용과 연결하라. | 모든 선행 연구를 단일 약한 baseline으로 묶기 |
| 어떤 관찰이 새 접근을 가능하게 하는가? | 관찰된 사실, 도출한 해석, 가설을 구분하라. | 아이디어를 결과로, 가설을 확정 사실로 쓰기 |
| 무엇을 어떻게 바꾸는가? | 핵심 선택과 그 작동 이유를 구체적으로 설명하라. | 구성요소 목록만 제시하거나 구현을 발명하기 |
| 무엇을 기여했고 어떻게 확인했는가? | 기여마다 뒷받침할 설계·분석·실험 위치를 연결하라. | 아직 없는 실험, 과장된 최초·최적 주장 |
| 어디까지 성립하는가? | 중요한 범위·제약을 소개의 주장과 함께 유지하라. | 제한을 뒤쪽으로 옮겨 소개의 주장을 무제한화하기 |

Introduction을 고쳤으면 contribution 문구가 Design과 Evaluation의 실제 내용과 대응하는지 확인하라. 기여 목록의 수를 맞추려고 하나의 결과를 여러 기여로 쪼개거나 미검증 주장을 덧붙이지 마라.

‘시스템을 제시한다’, ‘성능을 평가한다’라는 활동명만 있으면 무엇이 새롭고 어떤 관찰·분석으로 그 주장을 판별할 수 있는지 구체화하라. 정량 수치가 반드시 필요한 것은 아니다. 근거가 있는 기여에는 해당 절·그림을 가까이 연결하되, 존재하지 않는 절 번호나 참조 키를 만들지 마라. 실제 안내 기능이 없는 목차 나열은 줄이고, 복잡한 논문에서 독자를 돕는 안내는 유지하라.

**역방향 읽기:** 본문을 잠시 제외하고, 소개에 실제 적힌 문장만으로 ① 중요한 문제 ② 기존 접근의 구체적 한계 ③ 핵심 통찰·작동 아이디어 ④ 무엇을 어떻게 확인했고 어디까지 성립하는지를 짧게 복원하라. 복원에 저자의 구두 설명이나 뒤쪽 절의 지식이 필요하면 누락 위치를 표시하라. 이것은 [ATC 저자 안내](https://sigops.org/s/conferences/atc/2026/abstract.html)와 [1차 공개 심사 질문](https://sigops.org/s/conferences/atc/2026/review.html)에서 도출한 점검법이며 공식 합격 판정이 아니다.

학회가 특정 앞부분을 독립적으로 심사한다면 그 범위에 대해서도 같은 점검을 하라. ASPLOS의 첫 2쪽과 ATC의 별도 extended abstract 등 적용 범위는 [학회 카드](conference-guidance.md)와 현재 원문으로 확인하라. 페이지를 실제 보지 않았으면 ‘첫 2쪽 검증’ 대신 제공된 텍스트의 소개 수준 점검이라고 밝혀라.

## Design

독자가 ‘이 선택은 왜 필요하고, 어떻게 작동하며, 언제 실패하는가’를 이해하도록 편집하라.

1. **목표와 가정:** 최적화 목표, correctness 요구, 지원 범위, 자원·장애 모델을 정의하라. 가정과 보장을 섞지 마라.
2. **선택 이유:** 해당 문제에서 채택한 방식과 대안을 비교하라. 측정하지 않은 대안의 성능을 단정하지 마라.
3. **동작:** 입력·상태·결정·출력과 주요 경로를 순서대로 설명하라. 병렬 연산과 순차 연산을 문장 정리 과정에서 바꾸지 마라.
4. **불변조건과 예외:** 경계값, 실패·복구, 동기화·일관성 등 주장에 필요한 요소를 확인하라. 자료에 없는 프로토콜은 빈칸을 표시하라.
5. **비용과 범위:** 메타데이터, CPU, 메모리, 통신, 지연 등 실제 제공된 비용과 제약을 설명하라. ‘경량’만으로 대신하지 마라.
6. **구현 상태:** 제안, 프로토타입, 배포된 기능을 구별하라. 현재형으로 고치면서 계획된 기능을 구현된 기능으로 바꾸지 마라.

정확성 증명, 안전성, liveness, 최악 경우 상한은 별개의 주장이다. 테스트를 통과했다는 사실만으로 그 모두를 보장하지 마라. 시스템 이름을 주어로 쓰는 것은 동작 주체가 정확할 때만 허용하라.

### 동작 예제에서 일반적인 설계로 확장하기

독자가 메커니즘을 이해하는 데 도움이 될 때 사용하라. 단순한 설계에 불필요한 예제를 추가하지 마라. 다음 흐름을 참고하되 필요한 정의·전제는 예제보다 먼저 설명할 수 있다.

**작은 상황 설정 → 기존 방식의 문제 → 제안 방식의 결정·상태 변화 → 일반적인 규칙 → 예제가 다루지 못하는 조건**

- 한 요청 흐름, 상태 전이, 짧은 의사코드 또는 그림에서 같은 대상과 용어를 끝까지 추적하라. 제공된 설계에서 확인되는 동작만 시스템의 실제 동작으로 설명하라.
- 설명용으로 구성한 상황은 가상·도식적 예제라고 표시하라. 예제의 숫자·타이밍을 실측값, 대표 workload 또는 평균 개선으로 제시하지 마라.
- 관찰된 trace를 쓴다면 원자료와 범위를 연결하라. 유리한 trace 하나가 전체 효과나 correctness를 입증하지는 않는다.
- 직관 다음에는 실제 동작 규칙·가정·경계 조건을 설명하라. 직관을 단순하게 만들기 위해 실패·경쟁·비지원 조건을 삭제하거나 증명을 대체하지 마라.
- 설명 순서는 독자가 이해하는 데 필요한 순서로 정하라. 연구자가 시도한 모든 실패와 발견 과정을 나열하지 말되, 논거가 되는 실패 사례·운영 교훈은 유지하라.

이 스킬의 가상 예시 [19번](examples.md)과 같이 예제의 지위와 일반화 범위를 구분하라.

## Evaluation

결과 문장마다 다음 연결을 확인하라: **연구 질문 → 방법·비교 조건 → 측정 결과 → 해석 → 적용 범위**. 평가의 충분성·공정성까지 검토하는 요청에는 [empirical-evaluation.md](empirical-evaluation.md)의 일곱 관점과 대표 결과 감사를 적용하라.

| 검토 대상 | 구체적 확인 |
|---|---|
| 질문과 실험의 대응 | end-to-end 성능, 구성요소 기여, 비용, 민감도, 확장성 등 실제 주장에 필요한 실험이 있는가? 모든 논문에 이 실험들을 일괄 요구하지 마라. |
| 비교 조건 | 구현 버전·설정·튜닝, 자원 예산, 데이터·부하·품질 목표·SLO가 비교 가능한가? 차이는 설명하고 숨기지 마라. |
| 측정량 | latency/throughput/cost/quality의 정의, 단위, 측정 구간, percentile, 집계 수준이 명시되어 있는가? |
| 변동성 | 반복 횟수, 표본 단위, 오차 막대의 의미가 있는가? 없는 표준편차·CI·p-value를 만들지 마라. 한 run의 많은 요청을 독립 run 수로 세지 마라. |
| 인과성 | 다른 변수도 바뀌었는가? ablation·분석이 정확히 어느 주장까지 지지하는가? 메커니즘과 측정된 효과를 구분하라. |
| 결과 범위 | 평균·최대·기하평균·대표 workload를 구분했는가? 최대값이 맞더라도 나머지 분포와 악화 조건을 감춘 요약은 아닌가? |
| 제약과 부작용 | regression, 무효과, 실패, 비용·품질의 trade-off가 결론과 함께 제시되는가? |
| 재현 정보 | 결과를 해석·재현하는 데 필요한 설정·절차·artifact 위치가 있는가? 자료에 없는 값을 채우지 마라. |

도표에서 읽은 근삿값과 원자료의 정확한 값을 구분하라. 이미지의 시각적 차이만으로 통계적 유의성을 주장하지 마라. 집계된 백분위값의 평균을 전체 요청의 백분위값으로 바꾸지 마라. 평균들의 평균이나 비율의 평균을 계산할 때 가중치와 분석 단위를 확인하라.

숫자를 다시 표현할 때는 먼저 의미를 고정하라:

- 100 ms → 80 ms: 지연 20% 감소. 같은 작업의 시간비는 1.25배지만, 측정하지 않은 처리량이 25% 증가했다고 쓰지 마라.
- hit rate 80% → 84%: 4 percentage points 증가. 상대 증가는 5%이다. 두 표현을 섞지 마라.
- `up to 35%`: 최대 관찰 개선율이다. 평균 35%, 항상 35%, 모든 workload에서 35%라고 쓰지 마라.

`significant`가 일상적 강조인지 통계 용어인지 불명확하면 실제 검정 여부를 확인하거나 정확한 관찰 수치로 표현하라. 통계적 비유의성은 동등성이나 무효과의 증명이 아니다.

## Related Work와 Conclusion

Related Work는 기술·가정·적용 범위별로 비교하라. 기여표의 비교 대상이 실제로 포함되는지, 오래된 관련 접근과 최근의 직접 대안을 함께 고려했는지 보라. 단순히 인용 개수를 늘리지 마라. 확인하지 않은 논문에 새로운 한계를 귀속하거나 인용 키를 발명하지 마라. 원래 인용이 이동했으면 그 인용이 지지하는 주장이 유지되는지 확인하라.

상세 문헌 비교가 독자의 문제·아이디어 이해를 가로막으면 위치나 분량을 조정하라. 새로움과 동기를 판단하는 데 필요한 직접 선행 연구는 앞부분에 남겨라. Related Work를 무조건 마지막으로 이동하거나 Introduction의 관련 인용을 전부 제거하지 마라. 특히 앞부분만 심사하는 단계에서는 선행 대비 차이를 그 범위 안에서 설명해야 한다.

Conclusion은 본문에서 지지한 결과와 교훈, 중요한 한계를 묶어라. 새로운 수치, 최초 주장, 적용 범위를 도입하지 마라. 향후 계획은 완료한 결과와 구분하라.
