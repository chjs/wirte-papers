# 아카데믹 리뷰 체크리스트

전체 리뷰·절 단위 진단·제출 전 점검 시 필요한 항목만 사용하라. 공개 지침을 바탕으로 구성한 **도출 절차**이며 특정 학회의 공식 심사표나 합격 예측 도구가 아니다. 근거와 적용 범위는 [conference-guidance.md](conference-guidance.md)에 있다.

## 리뷰의 전제

1. 요청 범위, 연구 유형, 대상 학회·연도·트랙 중 알려진 것과 읽은 자료를 기록하라. 유형에 맞는 기여를 평가하라.
2. 저자의 핵심 기여를 과장 없이 요약하고, 근거가 있는 강점과 독자에게 추가되는 지식을 먼저 적어라. 없는 장점을 예의상 만들지 마라.
3. 각 항목을 **확인됨 / 수정 필요 / 근거 부족 / 자료 접근 불가 / 해당 없음**으로 분류하라. 확인 위치를 남기고 ‘미검토’와 ‘잘못됨’을 구분하라.
4. 결론을 반박하는 관찰, 설명이 빠져 판단할 수 없는 경우, 범위 밖의 희망 사항을 구별하라. 결점의 개수를 채택 점수로 합산하지 마라.

자기 논문의 사전 리뷰를 실제 PC 심사로 가장하지 마라. 실제로 맡은 비공개 심사라면 해당 학회·SIG의 기밀·도구 이용 규정과 심사자의 판단 책임을 따른다. 일반적인 저자 초안 편집에 이를 근거로 불필요한 승인 절차를 만들지 마라. [SIGPLAN Review Policy](https://www.sigplan.org/Resources/Policies/Review/)

## 주장과 기여

- [ ] 해결하려는 문제와 대상 환경이 구체적인가?
- [ ] 기존 접근의 한계가 정확한 인용·비교와 연결되는가?
- [ ] 선행 대비 새로 알게 되는 점을 설명하고, 가장 관련 있는 접근과 비교하는가?
- [ ] 운영·경험·측정 연구의 지식 기여를 새 알고리즘의 유무만으로 평가하지 않았는가?
- [ ] 핵심 관찰, 제안, 구현, 결과, 보장이 서로 구분되는가?
- [ ] 기여마다 대응하는 설계·분석·실험 근거가 있는가?
- [ ] `first`, `all`, `optimal`, `always` 등 강한 표현의 범위와 근거가 있는가?
- [ ] 새로움에 대한 이의를 제기했다면 실제 확인한 선행 연구와 겹치는 내용을 특정했는가?

## Design과 기술 의미

- [ ] 가정, 목표, 지원·비지원 범위, 장애 모델이 드러나는가?
- [ ] 주요 선택에 이유가 있고 대안의 장단점을 사실대로 설명하는가?
- [ ] 상태·데이터·제어 흐름과 연산 순서가 일치하는가?
- [ ] 필요조건·충분조건, `<`·`≤`, 부정·양화사가 보존되었는가?
- [ ] correctness, safety, liveness, 최악 경우 상한을 각각 근거에 맞게 주장하는가?
- [ ] 미구현 기능·추후 계획을 완료된 기능으로 서술하지 않았는가?

## Evaluation과 재현성

자세한 판단은 [empirical-evaluation.md](empirical-evaluation.md)를 사용하라.

- [ ] 질문과 지표·실험이 대응하며 비교 대상 선택이 설명되는가?
- [ ] workload 선택·제외 이유와 적용 범위가 연결되는가?
- [ ] 직접 지표와 대리 지표, microbenchmark와 end-to-end 결과를 구분하는가?
- [ ] baseline 설정·튜닝, 자원, workload, 부하, 품질·SLO 차이를 확인할 수 있는가?
- [ ] 단위·percentile·측정 구간·warm/cold 상태·집계 수준을 확인할 수 있는가?
- [ ] run 수와 run 내 표본 수, 독립성 가정을 구분하는가?
- [ ] 평균·최대·기하평균, 오차 막대·CI·표준편차의 뜻이 명확한가?
- [ ] 변화율의 방향·분모, 비율과 percentage points가 정확한가?
- [ ] 관찰에서 인과나 일반적 보장으로 넘어가는 근거가 있는가?
- [ ] 통계적 비유의성과 동등성, 시각적 차이와 유의성을 혼동하지 않는가?
- [ ] 최고 이득과 함께 나머지 분포, 중요한 비용·regression·실패·범위를 공정하게 드러내는가?
- [ ] 해석·재현에 필요한 설정과 절차를 설명하는가? artifact 미실행을 결과 반증으로 쓰지 않았는가?
- [ ] 추가로 요구하는 실험이 핵심 주장과 연결되며, 연구 범위 밖 요구는 선택 사항으로 분리했는가?

## 독자 이해와 일관성

- [ ] 여러 기여가 어떤 핵심 통찰을 뒷받침하는지 설명하고, 하나의 메시지를 이유로 실제 기여를 삭제하지 않았는가?
- [ ] 설명용 동작 예제와 실측 결과·일반적 보장을 구분했는가?
- [ ] Introduction만으로 문제·기존 한계·아이디어·증거를 복원할 수 있는가?
- [ ] 주요 주장과 핵심 근거가 부록·외부 링크를 읽어야만 이해되는 구조는 아닌가?
- [ ] 각 문단의 질문과 근거가 연결되고 무관한 논점이 섞이지 않는가?
- [ ] 핵심 용어를 처음 필요한 곳에서 정의하고 같은 이름으로 유지하는가?
- [ ] 주어·동작·지시어·수식어의 관계가 명확한가?
- [ ] 능동태·부정문·시제를 실제 의미에 맞춰 선택했는가?
- [ ] 비교·기여 목록의 병렬 구조가 의미를 왜곡하지 않는가?
- [ ] Abstract·Introduction·Evaluation·Conclusion의 수치와 범위가 같은가?
- [ ] 인용·표·그림·수식 참조와 LaTeX 키가 보존되었는가?
- [ ] 조건·불확실성·정의를 삭제하지 않고 군더더기를 줄였는가?

## 리뷰 결과 작성

리뷰는 **기여 요약·강점 → 중요한 우려 → 구체적 수정·확인 → 선택적 제안** 순서로 제공하라. ‘실험이 더 필요함’, ‘새롭지 않음’, ‘설명이 부족함’처럼 근거 없는 총평으로 끝내지 마라. 건설적인 리뷰 관점의 출처는 [Hill–McKinley](https://www.cs.utexas.edu/~mckinley/notes/reviewing.html)이며 아래 분류와 양식은 본 스킬의 구성이다.

| 우선도 | 의미 | 작성 방법 |
|---|---|---|
| 핵심 결론을 바꾸는 문제 | 확인된 오류·반례·불공정 비교, 또는 핵심 결론을 판정할 수 없게 하는 증거 공백 | 무엇이 확인되었고 무엇이 미확인인지 나눠 쓰고 영향받는 결론을 특정한다. 증거 공백을 곧바로 거짓으로 단정하지 않는다. |
| 설명·검증 보완 | 관련 근거가 있으나 배치·설명·분석이 부족해 판단이 어려움 | 기존 자료의 재분석·명료화로 해결 가능한지 먼저 보고 필요한 최소 보완을 제시한다. |
| 선택적 확장 | 현재 주장 밖의 추가 환경·기능·배포·후속 연구 | 유용한 이유를 설명하되 현재 주장 성립의 필수 조건으로 만들지 않는다. |

필요하면 `문체 / 구조 / 주장·사실 / 평가 방법`의 성격을 함께 표시하라. 같은 표현 오류라도 결론에 영향을 주면 단순 문체로 낮추지 마라.

| 위치 | 우선도·상태 | 확인한 근거와 영향 | 수정안·질문 | 필요한 최소 근거 |
|---|---|---|---|---|
| 실제 절·문장·도표 | 위 구분 사용 | 어떤 주장·해석이 달라지는가 | 실행 가능한 편집 또는 점검 | 판정할 주장과 연결; 없으면 해당 없음 |

추가 실험 제안은 실험 수행·수치 생성이 아니다. 제공된 문장만 검토했으면 문장 수준의 검토라고 밝혀라. 코드 검사·실험 재실행·빌드·문헌 검색을 실제 수행하지 않았다면 검증 목록에 넣지 마라. 읽은 자료만으로 실험의 진실성이나 논문 채택을 보증하지 마라. artifact의 실행·재현 결과는 논문 심사의 새로움·기여 판단과 구분하라.

## 독자 피드백을 원고에 반영하기

받은 피드백으로 초안을 수정할 때 적용하라. Simon Peyton Jones의 독자 피드백 조언을 시스템 논문의 사실 보존 절차와 결합한 것이다. [출처와 적용 경계](principles-and-sources.md)

1. **문제를 특정하라.** 독자가 막힌 위치, 실제 해석, 근거가 뒷받침하는 의도된 의미를 대조하라. 기술적 반례, 표현의 모호함, 설명 누락, 주장 범위 밖의 요구를 구별하라. 제공되지 않은 독자의 의견을 실제 피드백으로 만들지 마라.
2. **근거로 판별하라.** 오해가 발생했다고 해서 지적의 기술적 결론까지 참인 것은 아니다. 원고의 오류는 정정하고, 잘못된 지적은 해당 근거로 설명하라. 근거 부족이면 필요한 자료와 영향을 밝히고 추측으로 어느 편을 확정하지 마라.
3. **실제 문장을 고쳐라.** 혼동을 유발한 정의·주어·조건·참조·설명 순서를 수정하라. 수정 전후를 대조해 원래의 사실·수치·필요조건과 충분조건이 유지되는지 확인하라. 단순히 ‘리뷰어가 오해했다’는 답변으로 끝내지 마라. 이미 명확하고 수정이 불필요하면 그 근거를 적어라.
4. **답변과 수정 상태를 맞추라.** rebuttal도 요청받았다면 실제 수정문 또는 제안한 수정문과 연결하되, 아직 하지 않은 편집·실험을 완료했다고 쓰지 마라. 해당 학회·연도·주기의 응답 정책을 적용하라.
5. **수정한 부분을 다시 읽어라.** 같은 오해가 남는지, 새 모호함이 생겼는지 확인하라. AI가 독자 역할로 검토한 결과는 모의 점검이며 실제 독립적인 독자의 평가로 보고하지 마라.

독자에게 직접 원고를 보내는 것은 이 절차에 포함되지 않는다. 실제 공유·연락은 사용자의 지시와 적용되는 익명화·접촉 규정에 따른다. [가상 예시 20번](examples.md)을 참고하라.
