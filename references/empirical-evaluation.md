# Evaluation의 주장과 근거 점검

Evaluation 작성·실험 설계에 대한 리뷰·정량 주장 감사 때 읽어라. [SIGPLAN의 2018 지침](https://www.sigplan.org/Resources/EmpiricalEvaluation/)이 제시한 일곱 관점을 시스템 논문 편집 절차로 재구성했다. 세부 질문과 표는 **이 스킬의 도출 절차**이며 원문 심사표가 아니다. ASPLOS 2027은 이 지침을 명시적으로 기대하지만, 모든 시스템 학회의 동일한 필수 양식으로 취급하지 마라.

## 1. 먼저 연구 질문과 판정 단위를 정하라

평가 자료를 단순히 나열하지 말고 각 핵심 주장에 대해 다음을 연결하라. 한 문장 교정에서는 내부적으로만 확인해도 된다.

| 주장·범위 | 필요한 관찰 또는 분석 | 자료 위치·상태 | 현재 허용되는 결론 |
|---|---|---|---|
| 대상·환경·baseline·지표·방향 | 이 주장을 지지하거나 반박할 결과 | 그림/표/코드/증명/메모, 확인됨·부족·충돌 | 측정 범위의 관찰 / 제한된 해석 / 아직 목표 |

추가 실험을 요구할 때는 **검증하려는 주장 → 현재 근거의 구체적 빈틈 → 필요한 최소 비교·분석 → 결과에 따라 달라질 결론**을 설명하라. 논문의 범위 밖 확장은 선택 사항으로 분리하라. 자료 부족은 시스템이 실패했다는 관찰이 아니다.

## 2. 일곱 관점으로 읽기

### A. 주장의 명료성

지표, 비교 대상, 적용 환경과 주장의 강도를 고정하라. 설계 목표, 실제 구현, 관찰 결과, 일반 보장을 구분하라. ‘효율적’, ‘확장 가능’, ‘실용적’이 어느 비용·규모·제약을 뜻하는지 근거에 연결하라. 모든 주장을 성능 수치로 바꿀 필요는 없다.

### B. 적절한 비교

가장 관련 있는 선행 접근과 현실적 대안을 선택한 이유를 확인하라. 저자가 작성한 약한 구현만으로 분야 전체를 대표하지 마라. 버전·컴파일·튜닝·자원·품질/SLO 차이를 확인하고, 동등하지 않은 조건은 이유와 영향을 설명하라. 공정함이 무조건 동일 설정을 뜻하지는 않는다. 각 시스템의 적절한 설정과 비교 목적을 함께 판단하라.

### C. workload 선택의 타당성

주장 대상과 선택한 workload·입력·규모가 어떻게 연결되는지 확인하라. 표준 suite, 실제 trace, 합성 부하 중 질문에 맞는 것을 쓰고 선택·제외 이유를 기록하라. 일부 결과만 받은 경우 전체 분포를 추정하지 마라. 모든 논문에 production workload를 강제하지 않되, microbenchmark만으로 서비스 전체의 개선을 확정하지 마라.

### D. 자료 분석의 적절성

독립 실험 단위와 run 안의 요청을 구분하라. 반복·변동성·오차 막대의 뜻과 집계 수준을 확인하라. 평균, 비율, percentile은 연구 질문과 분모에 맞춰 해석하라. 자료 없이 CI·유의성·반복 횟수를 만들지 마라. 모든 논문에 같은 검정, 반복 횟수, geometric mean을 강제하지 마라. 차이를 입증하지 못한 결과를 동등성 증명으로 바꾸지 마라.

### E. 주장에 맞는 지표

직접 지표와 대리 지표를 구분하라. 예를 들어 cache miss 감소는 실행시간·에너지 감소의 직접 측정이 아니다. 이를 대리 지표로 쓰는 이유와 한계를 명시하라. 핵심 주장에 영향을 주는 준비·학습·컴파일·메타데이터·메모리 비용이나 품질 저하가 빠졌는지 확인하라. 모든 자원 비용을 무조건 측정하라는 뜻은 아니다.

### F. 실험 설계와 설명

핵심 결과를 해석하는 데 필요한 환경·설정·절차를 본문에서 파악할 수 있게 하라. warm-up, cache 상태, 입력 생성, 측정 구간, 부하·도착 모델, train/evaluation 분리를 해당 연구에 맞춰 확인하라. open-loop나 closed-loop를 일괄 선택하지 말고 실제 대상과 측정 질문에 맞춰라. ablation·통제·민감도 분석은 특정 메커니즘 주장에 필요한 경우 제안하고, 실험이 제공하는 식별 범위를 넘어서 인과를 단정하지 마라.

### G. 결과 제시의 충실성

지표·단위·정규화 기준·집계 방식·표본 수·오차 표시를 독자가 해석할 수 있게 하라. 축 범위와 로그·절단·정규화가 차이를 왜곡하지 않는지 확인하라. 불확실성에 비해 과도한 유효숫자를 피하라. 표·그림을 다시 만들 경우 원자료 없이 시각적 추정치를 정밀값처럼 표시하지 마라. 그림 제목·본문 결론이 실제 측정 범위보다 강해지지 않게 하라.

일곱 관점의 출처: [SIGPLAN checklist PDF](https://raw.githubusercontent.com/SIGPLAN/empirical-evaluation/master/checklist/checklist.pdf). 구체적인 작업 절차에는 [Heiser의 benchmarking 조언](https://gernot-heiser.org/benchmarking-crimes.html)에서 제기한 비교·선택·비용 문제도 반영했다. 두 자료를 기계적인 탈락 규칙으로 쓰지 마라.

## 3. 대표 결과를 따로 감사하라

Abstract·Introduction·Conclusion에 들어가는 수치에는 정확성과 대표성을 함께 확인하라.

1. **모집 범위:** 어떤 workload·규모·설정을 평가했고 무엇을 제외했는가?
2. **집계 의미:** 최대값인가, workload별 변화의 평균인가, 요청을 합친 값인가? 서로 바꾸지 마라.
3. **나머지 결과:** 개선이 없거나 악화된 조건과 중요한 비용이 있는가? 제공되지 않았다면 ‘없음’으로 쓰지 마라.
4. **요약 적절성:** 최대 이득만 제시하면 독자가 일반적 이득으로 오해할 가능성이 있는가? 자료가 있으면 범위·집계·regression을 함께 쓰고, 없으면 최대값이라는 한정을 유지하며 대표성 미확인을 알리라.
5. **원인과 적용 범위:** 동시 변화가 원인을 분리했는가? 측정하지 않은 환경까지 확장했는가?

`up to`를 보존하는 것만으로 공정한 요약이 완성되지는 않는다. 반대로 전체 자료가 없다고 최대값을 임의로 평균값으로 고치지도 마라. 독자가 숫자를 잘못 일반화하지 않게 필요한 한계를 함께 전달하라.

## 4. 논문과 artifact의 증거를 구분하라

논문 리뷰는 연구의 주장과 그 근거를 평가한다. artifact 점검은 제공된 코드·데이터·문서로 실행·재현할 수 있는지를 확인한다. 실행 성공이 새로움이나 모든 결론의 타당성을 증명하지 않고, 환경을 확보하지 못한 실행 실패도 논문의 결과가 거짓임을 증명하지 않는다. [ASPLOS 2027 artifact reviewer 안내](https://www.asplos-conference.org/asplos2027/for-reviewers/)

artifact 검토까지 요청되면 결과/그림 → 실행 절차 → 환경·입력 → 기대 산출물을 연결하라. 실제로 실행한 범위, 문서로만 확인한 범위, 실행하지 못한 이유를 구분하라. badge나 코드 공개를 모든 초안의 필수 통과 조건으로 만들지 마라.
